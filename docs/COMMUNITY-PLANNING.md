# Community planning mode (prototype)

Typecast's Director has a second mode next to **Film production**: **Community planning**. It is a focused, secondary use of the same engine: pre-incident candidate-site review for volunteer coordination and supply distribution or staging. It is a prototype planning aid. It has not been used by any organization, and no public benefit has been measured.

## What it is not
- Not real-time evacuation routing, not emergency dispatch, not live coordination, and it sends no messages and holds no contacts.
- Not an approval of any site or shelter. There is no "safe", "approved" or "certified" badge anywhere, and "reported OK" never means verified.
- It does not derive headcount capacity, exits, clearance, safety or current availability from floor area, images, listings or parking. It does not call any hazard or shelter API, and it does not send licensed assets to a model or provider.

## How it works
1. **Mode control** at the top of the page switches `Film production | Community planning` (Film is the default). Each mode has its own script, plan, notes and constraints. Switching never edits the other mode's work; film takes cannot become a community plan, and a community need cannot be parsed as a film scene.
2. **Site needs.** Describe each site you need as a short paragraph (a title line, then what it must offer); blank lines separate needs (up to 8). `Title | needs` lines also work. A reading of your text is shown before you build. `INT.`/`EXT.` has no special meaning here. Supply trucks and volunteer cars are optional vehicle constraints.
3. **Find candidate sites** uses the same retrieval, property association, solver and rejection flow as film mode, over the same recorded evidence. The stage shows the real indexed frame labelled "Preparedness planning · candidate site · not an approved site". "Rule out site" is the film mode's rejection; "Try another site" swaps a need to another candidate in the current pool.
4. **Site fit evidence** (collapsed, same rules as the film Fit check): similarity is not a fit score; availability follows the source status; vehicles use the source's own sufficiency flag; "at least / no more than / more than / less than" with m², ft² or a ceiling height are compared only with index estimates (estimates stay "consistent (estimated)"); toilets, power, water, ramps and similar are listed as "not in the data". Only simple wording is read; everything else in your text stays for a person to judge.
5. **Site tab** per need: a requested participant or volunteer count (a request, never a capacity), seven coordinator checks (owner permission and access; verified occupancy and capacity; exits and fire inspection; accessibility; toilets; power and water; current hazards and site condition), optional follow-ups with an owner name (up to 6), notes, and an optional independently verified capacity that is kept only if you also state where it came from. Every check starts as **unknown**; you can mark it "reported OK" or "reported problem" with a note. These are human-reported by you, are labelled so everywhere, and are never source-measured. Records belong to a specific candidate site, so swapping the site does not carry another site's reports.
6. **Site brief (printable)** in the Export tab, built with the existing export mechanics (a single offline HTML file with a restrictive content-security policy, then print to PDF): identity statement, "NEEDS VERIFICATION" with the count of unknown checks, optional reviewer name and date, per need the requested count beside any verified capacity (never a comparison or a computed capacity), the real indexed frame with its source warnings, fit evidence, the seven checks as reported, follow-ups, notes, other candidate sites in the pool (not assessed) and a verification checklist. Project JSON saves the mode, brief details, needs and per-site reports (strictly validated; see `docs/team/CONTRACT-CHANGES.md`). OK reports restored from a file or a draft are shown as "restored; re-verify".

## Human steps that remain
Owner permission and access; independent verification of occupancy and capacity (inspection, permit or owner letter); exits and fire inspection; accessibility; toilets; power and water; current hazards and site condition; a site visit. Typecast cannot do any of these.

## Local draft recovery (both modes)
Each mode keeps one local draft in this browser's local storage (script text, constraints, and a minimal validated project: scene text, takes or reports, notes and identifiers; never images, keys, provider data or source rows). It is plain readable text, not encrypted or synced, so clear it on a shared computer. After a refresh or crash the film draft is restored at load and the community draft when you first open that mode, with a message and `Discard this draft` and `Stop keeping drafts` buttons plus a `Keep a local draft` switch and `Clear saved draft` in the Export tab. Restoring rebuilds evidence from the current data through the same validator as a file import, so availability or safety claims are never restored and frames that no longer match become review drafts. Autosave is paused while a saved draft is not reflected on screen (for example if the evidence request fails), never writes the untouched demo state, and quota or blocked storage only produces a note. With several tabs open the last one to save wins.
